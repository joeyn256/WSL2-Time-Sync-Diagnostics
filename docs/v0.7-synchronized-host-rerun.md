# v0.7.0 synchronized-host rerun closure

Released: 2026-10-15

## Question

v0.7 attempted to answer:

> Does the previously observed Ubuntu 24.04 WSL2 clock pathology reproduce when the Windows host itself satisfies a frozen external-time synchronization admission gate?

The answer is **not established**, because the host never reached the required admission state and the synchronized-host Ubuntu scientific campaign was never launched.

## Frozen scientific state

At closure:

- scientific launches consumed: **0 / 8**;
- unknown scientific launches: **0**;
- replacements consumed: **0 / 2**;
- Seq 1 / P24-A ended as `CYCLE_OPEN -> PRE_ADMISSION FAIL -> CYCLE_CLOSED_NOT_LAUNCHED`;
- no `LAUNCH_CONSUMED` record exists;
- Seq 2 was never opened;
- the separate formal host-admission observation remained **UNUSED**;
- no synchronized-host Ubuntu 24.04 or Ubuntu 26.04 scientific run occurred.

These facts matter: the Windows-host admission attempts are infrastructure evidence, not guest timing measurements.

## Final host-normalization attempts

The project deliberately bounded Windows-time work rather than repeatedly modifying the host.

### Temporary-zero + `/resync /rediscover`

A guarded attempt temporarily set the existing `MaxAllowedPhaseOffset` DWORD from its captured value of 1 to 0, refreshed W32Time configuration, and issued exactly one:

```text
w32tm /resync /rediscover
```

Windows logged a clock correction of about **-2.146 s** and a synchronization event, but the command reported that no time data was available and the service did not remain in the required synchronized state.

The original DWORD value was restored and restoration was proven.

### Final temporary-zero + plain `/resync`

The last permitted Windows-time normalization attempt repeated the guarded temporary-zero transaction but changed the sole synchronization command to:

```text
w32tm /resync
```

The command was dispatched exactly once.

Observed command result:

```text
Sending resync command to local computer
The computer did not resync because no time data was available.
```

The process exit code was 0, but the explicit semantic failure text was treated as a veto.

During the command lifetime Windows also logged:

- NtpClient receiving valid time data from `time.windows.com,0x9`;
- a system-time change of about **-0.121 s**;
- a Time-Service synchronization event with `time.windows.com,0x9`.

Those events are preserved as corroborating state only. They did not override the explicit resync failure or establish a usable post-command synchronization state.

Afterward W32Time reported an unsynchronized state (Leap Indicator 3, stratum 0, state machine Unset / last-sync error), so the packet did not proceed to the triage screen or formal host admission.

## Restoration

The final attempt restored the original Windows Time configuration immediately through its mandatory `finally` path.

Restoration was verified twice:

1. by the elevated executor; and
2. by a separate elevated verifier.

Both observed the exact original `MaxAllowedPhaseOffset` DWORD bytes and effective local value, successful restoration `w32tm /config /update`, no applicable policy override, and no unresolved packet-owned W32Time process.

Terminal disposition:

```text
FINAL_W32TIME_CORRECTION_FAILED — RESTORATION_PROVEN
```

## Why v0.7 stops here

The final packet explicitly prohibited another Windows-time repair attempt after an executed unsuccessful result. This prevents repeated host modification from turning an admission problem into an open-ended tuning exercise.

Therefore v0.7 closes with:

- host-admission infrastructure exercised;
- final correction mechanisms attempted;
- restoration proven;
- synchronized-host scientific rerun **not achieved**;
- prior public guest-side/historical observations preserved without reinterpretation.

## What v0.7 does not claim

v0.7 does not claim that:

- Windows or WSL fixed the original pathology;
- the pathology still reproduces under a synchronized host;
- Ubuntu 26.04 is universally more accurate than Ubuntu 24.04;
- the temporary-zero setting itself caused either observed clock step;
- `/rediscover` caused the earlier semantic failure;
- the six planned synchronized-host cases were run.

## Reproduction

Another host can use the public CLI and documented measurement methods to:

1. establish its own Windows-host synchronization state;
2. run bounded WSL guest probes;
3. compare `CLOCK_MONOTONIC` against `CLOCK_MONOTONIC_RAW`;
4. preserve raw evidence and environment/version information;
5. report admission failure separately from guest scientific results.

The private operational controller used for this host contained machine-specific evidence paths and governance machinery and is intentionally not published as a general-purpose host modification tool.
